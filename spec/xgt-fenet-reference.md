## 1. 애플리케이션 헤더 레이아웃 — 20바이트

신뢰도: **중간** (20바이트 총 길이와 필드 구성은 일관되나, Position/BCC 바이트의 의미에 이견 여지)

| 오프셋 | 크기 | 필드 | 값 / 규칙 | 신뢰도 |
|---|---|---|---|---|
| 0 | 10 | Company ID | ASCII `"LSIS-XGT"` + `0x00 0x00` (10바이트로 패딩) | 높음 |
| 10 | 2 | PLC Info | 예약. 요청은 보통 `0x0000` | 중간 |
| 12 | 1 | CPU Info | CPU 종류 코드. **XGI 값 불확실 → 요청 값을 에코한다** | 낮음 |
| 13 | 1 | Source of Frame | 요청(클라이언트→PLC) `0x33` / 응답(PLC→클라이언트) `0x11` | 높음 |
| 14 | 2 | Invoke ID | uint16 LE. **응답에 그대로 에코** | 높음 |
| 15+ | 2 | Length | uint16 LE. 헤더 뒤 애플리케이션 인스트럭션의 바이트 수 | 높음 |
| 18 | 1 | FEnet Position | 모듈 슬롯 위치. **요청 값을 에코한다** | 낮음 |
| 19 | 1 | Reserved / BCC | 체크섬. **계산 범위 불확실 → 수신 시 검사하지 않고, 송신 시 헤더 0..18 합의 하위 바이트를 넣는다(설정 가능)** | 낮음 |

정확한 오프셋: `0..9` CompanyID, `10..11` PLCInfo, `12` CPUInfo, `13` Direction,
`14..15` InvokeID, `16..17` Length, `18` Position, `19` BCC. (합 20)

> **⚠️ 미검증 지점** — Length 필드가 "헤더 제외 데이터부 길이"인지 "전체 프레임 길이"인지가
> 프레이밍 전체를 좌우한다. 여기서는 **헤더 제외 데이터부 길이**로 구현했다(신뢰도 높음).
> 캡처 프레임 1개만 있으면 즉시 확정된다: `전체 길이 - 20 == Length 필드값` 인지 보면 된다.

## 2. 명령 코드 / 데이터 타입 코드

### 명령 코드 (데이터부 오프셋 0, uint16 LE)
신뢰도: **높음**

| 값 | 뜻 |
|---|---|
| `0x0054` | 읽기 요청 |
| `0x0055` | 읽기 응답 |
| `0x0058` | 쓰기 요청 |
| `0x0059` | 쓰기 응답 |

### 데이터 타입 코드 (데이터부 오프셋 2, uint16 LE)
신뢰도: **높음** (연속 `0x0014` 는 중간)

| 값 | 뜻 | IEC 대응 |
|---|---|---|
| `0x0000` | 비트 | `%MX` |
| `0x0001` | 바이트 | `%MB` |
| `0x0002` | 워드 | `%MW` |
| `0x0003` | 더블워드 | `%MD` |
| `0x0004` | 롱워드 | `%ML` (본 구현 미지원 — 거절) |
| `0x0014` | 연속(블록) | 시작 주소 + 바이트 수 |

## 3. 데이터부 레이아웃

### 개별 읽기 요청 (`0x0054`, 타입 ≠ `0x0014`)
신뢰도: **높음**
```
uint16 LE  Command      = 0x0054
uint16 LE  DataType
uint16 LE  Reserved     = 0x0000
uint16 LE  BlockCount   (개별 읽기 최대 블록 수는 매뉴얼 미확인 → 본 구현 기본 무제한)
  BlockCount 회 반복:
    uint16 LE  VarNameLength
    ASCII      VarName    예: "%MW100"
```

### 개별 읽기 응답 (`0x0055`)
신뢰도: **중간**
```
uint16 LE  Command      = 0x0055
uint16 LE  DataType     (요청 에코)
uint16 LE  Reserved     = 0x0000
uint16 LE  ErrorStatus  0x0000 = 정상
uint16 LE  BlockCount   (오류 시 오류 정보로 쓰인다는 자료도 있음 — 낮음)
  BlockCount 회 반복:
    uint16 LE  DataSize
    bytes      Data      (리틀엔디안)
```

### 연속 읽기 요청 (`0x0054`, 타입 `0x0014`)
신뢰도: **중간**
```
uint16 LE  Command = 0x0054, DataType = 0x0014, Reserved = 0x0000, BlockCount = 0x0001
uint16 LE  VarNameLength
ASCII      VarName          시작 주소
uint16 LE  DataCount        읽을 바이트 수
```

### 개별 쓰기 요청 (`0x0058`, 타입 ≠ `0x0014`)
신뢰도: **해소** — 값 구간 배치를 프레임 길이로 판별하므로 더 이상 가정이 필요 없다
```
uint16 LE  Command = 0x0058, DataType, Reserved = 0x0000, BlockCount
  [묶음(Grouped) 가정 — 본 구현 기본]
    BlockCount 회: uint16 LE VarNameLength, ASCII VarName
    BlockCount 회: uint16 LE DataSize,      bytes Data
```
> **값 구간에 블록별 크기 필드가 있는지 없는지가 원래 불확실했다** — 그리고 이것이 실제로
> "LabVIEW 에서 쓰기가 안 된다" 의 원인이었다. 크기 필드가 없는 프레임을 받으면 값의 앞 2바이트를
> 길이로 오독해 해석 실패로 거절했다.
>
> **이제 프레임 길이로 판별한다.** 헤더의 Length 필드가 데이터부 크기를 정확히 주므로
> 남은 바이트 수가 `N × (2 + 요소크기)` 면 크기 필드 있음, `N × 요소크기` 면 없음으로 확정된다
> (두 값은 절대 같을 수 없다). 추측이 사라졌다.
>
> **값의 길이는 이름의 폭이 아니라 프레임이 정한다(현장 확인, 2026-08-14).**
> 마스터가 데이터 타입으로 폭을 정하고 변수명은 시작 위치로만 쓰는 경우가 있다 —
> 실제로 `이름 %MW000(2바이트) + 값 4바이트` 프레임이 관측됐다. 이름 폭과 값 길이가
> 다르다는 이유로 거절하면 마스터가 보낸 데이터가 통째로 버려진다.
> 시작 위치는 이름이, 길이는 실제 온 바이트 수가 정한다(비트 주소는 예외 — 1바이트 고정).

> BlockCount = 1 이면 묶음/교차(Interleaved) 두 해석은 바이트열이 동일하다.
> 2블록 이상 교차 배치를 쓰는 마스터를 위해 `XgtFenetOptions.WriteBlockLayout` 설정은 남겨 둔다.

### 연속 쓰기 요청 (`0x0058`, 타입 `0x0014`)
신뢰도: **중간**
```
uint16 LE  Command = 0x0058, DataType = 0x0014, Reserved = 0x0000, BlockCount = 0x0001
uint16 LE  VarNameLength
ASCII      VarName
uint16 LE  DataCount   ← 없는 마스터도 있다. 아래 참조
bytes      Data
```
> **`DataCount` 유무는 추측하지 않는다 — 프레임 길이로 판별한다(해소, 2026-08-03).**
> 헤더 Length 가 데이터부 크기를 정확히 주므로 변수명 뒤 남은 바이트 수를 알 수 있다.
> 선행 2바이트가 `남은 바이트 − 2` 와 정확히 같을 때만 `DataCount` 로 인정하고,
> 아니면 남은 전체를 `Data` 로 본다. 무검증으로 2바이트를 개수로 읽으면 개수 필드가 없는
> 마스터의 데이터 첫 2바이트를 길이로 오독해(예: `0xFFFF` → 65535바이트) 쓰기가 통째로 실패한다.

### 쓰기 응답 (`0x0059`)
신뢰도: **중간**
```
uint16 LE  Command = 0x0059, DataType(에코), Reserved = 0x0000, ErrorStatus, BlockCount = 0x0000
```

## 4. 변수명 표기 규칙

신뢰도: **높음**

직접변수 ASCII 문자열. `%` + 영역(`I`/`Q`/`M`) + 크기(`X`/`B`/`W`/`D`) + 10진 오프셋.
예: `%MW100`, `%MX801`, `%IW80`, `%QX1024`.
길이는 2바이트 LE 접두. 본 구현은 `IecAddress` 파서를 그대로 재사용한다(M1 골든 벡터로 고정된 파서).

## 5. 에러 상태 코드

신뢰도: **낮음** — 코드 표 값이 불확실

확실한 것: `ErrorStatus = 0x0000` 이 정상이라는 것 (신뢰도 높음).
0이 아닌 값의 **구체적 표 값은 확인되지 않았다.** 본 구현은 아래 잠정 매핑을 쓰고,
`XgtFenetOptions.ErrorCodeMap` 으로 재정의할 수 있게 노출한다.

| 추상 사유 (`PlcErrorReason`) | 잠정 코드 | 신뢰도 |
|---|---|---|
| `None` | `0x0000` | 높음 |
| `InvalidAddress` | `0x0010` | 낮음 |
| `RangeExceeded` | `0x0011` | 낮음 |
| `UnsupportedDataType` | `0x0012` | 낮음 |
| `InvalidBlockCount` | `0x0013` | 낮음 |
| `InvalidDataSize` | `0x0014` | 낮음 |
| `DataSizeMismatch` | `0x0015` | 낮음 |

> **⚠️ 여기가 가장 위험한 지점이다.** LabVIEW가 오류 코드를 사람에게 보여주기만 하면 티가 나지만,
> 코드 값으로 분기하면 조용히 잘못 동작한다. **매뉴얼 §에러 코드 표를 확인해 위 값을 교체할 것.**

## 8. 검증 절차 — 이 문서를 신뢰할 수 있게 만드는 방법

아래 중 **하나만 해도** 대부분의 불확실성이 사라진다.

### A. 캡처 1개로 헤더 확정 (10분, 장비 불필요)
```bash
nc -l 2004 > fixtures/labview-capture/req_read.bin
# LabVIEW 대상 IP를 127.0.0.1 로 → 읽기 1회 → Ctrl+C
xxd fixtures/labview-capture/req_read.bin
```
확인할 것:
1. 선두 10바이트가 `4C 53 49 53 2D 58 47 54 00 00` 인가 → Company ID 확정
2. 오프셋 13 이 `0x33` 인가 → 방향 바이트 확정
3. 오프셋 16..17 (LE) 값이 `전체 길이 - 20` 과 같은가 → **Length 의미 확정 (가장 중요)**
4. 오프셋 12 의 실제 CPU Info 값 → 문서에 기록
5. 오프셋 19 의 BCC 가 헤더 0..18 합의 하위 바이트와 같은가 → BCC 범위 확정
6. 오프셋 20..21 이 `54 00` 인가 → 명령 코드 확정

### B. 매뉴얼로 에러 코드 표 확정 (필수)
§5 의 잠정 코드는 **거의 확실히 틀렸다.** 매뉴얼의 에러 상태 코드 표로 교체할 것.

### C. LabVIEW 왕복으로 종단 검증
접속 → 값 읽기 → LabVIEW 화면 값이 시뮬레이터 UI 값과 일치하는지.
일치하면 요청 파싱과 응답 생성이 실질적으로 맞다는 강한 증거다(LabVIEW 가 오라클 역할을 한다).

### 검증 결과를 기록하는 곳
확인한 항목은 이 문서의 신뢰도 등급을 **높음**으로 올리고 출처(매뉴얼 페이지 / 캡처 파일명)를 적는다.
전 항목이 `높음` 이 되면 위 경고 배너를 지우고, `XgtFenetCodec.IsDraft` 를 `false` 로 바꾼다
(그러면 앱의 "미검증 코덱" 경고가 사라진다).
